# Spcod Relay — Zero-knowledge dumb relay

[中文](README.md) · [Deployment guide](docs/DEPLOYMENT.en.md) · [Self-hosting configuration](docs/SELF_HOSTING.md) · [Protocol](docs/PROTOCOL.md) · [Privacy](docs/PRIVACY.md)

A self-hosted relay for Spcod harness remote control. It routes end-to-end encrypted data between phones and computers without reading code, prompts, conversations, or scheduled-task content.

## Check and install dependencies

Deployment only requires Bash, Git, Docker Engine 24+, Docker Buildx, and the Docker Compose 2.20+ plugin. Check them first:

```bash
git --version
docker --version
docker compose version
docker info
```

On Ubuntu 22.04/24.04, install all dependencies from Docker's official apt repository:

```bash
sudo apt update
sudo apt install -y git ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
```

Run `sudo docker run --rm hello-world` to verify the installation. To let a regular user run Docker directly, run `sudo usermod -aG docker "$USER"`, then log out and back in. For other distributions, use the [official Docker installation guide](https://docs.docker.com/engine/install/).

## One-command deployment

```bash
git clone https://github.com/spcodhu/Spcod-relay.git
cd Spcod-relay
./deploy.sh --check   # Optional: show versions and check Docker daemon access
./deploy.sh
```

The script generates and persists the relay identity key `RELAY_SECRET_KEY` and a random self-hosted access key, builds **one image containing both the relay and mobile PWA**, starts the service, and waits for its health check. The PWA is built during the Docker build from a pinned Spcod source commit. Node.js, pnpm, file uploads, and manual Compose edits are not required.

`RELAY_SECRET_KEY` must be generated by `deploy.sh` and stored in `deploy/relay.env`; production refuses to start without it. Do not rotate it casually: rotation invalidates all issued device grants, requiring devices to reconnect over LAN for renewal or scan a new QR code.

When deployment finishes, the terminal prints the relay URL and access key. In **Spcod harness → Settings → Remote Control → Self-hosted**, enter:

- Relay URL: `ws://<SERVER_IP>:8787`
- Access key: the printed `Access key`

Configuration and credentials are stored in `deploy/relay.env`, which is ignored by Git. Direct HTTP/WebSocket is intended for temporary or private-network use; enable a domain and HTTPS for a long-lived public deployment.

Maintainers deploy the official public instance with `./deploy.sh --domain spcod-relay.hlt.cab --public`. `--public` persists public mode without an access key, but hosts must still present v3 ownership proofs and devices must still hold desktop-issued grants. Ordinary self-hosted deployments generate and require an access key by default.

## Verify installation and deployment

- **Browser health page**: open `http://<SERVER_IP>:8787/health`, or `https://relay.example.com/health` after configuring a domain. It follows the browser's Chinese or English language preference and only shows service status, protocol version, and check time—never credentials or message data.
- **Command line and automation**: run `curl --fail http://<SERVER_IP>:8787/health`, replacing the URL with `https://relay.example.com/health` after configuring a domain. A healthy service returns `{"ok":true,"version":3}`.
- **Container status**: run `docker compose --env-file deploy/relay.env -f deploy/docker-compose.yml --profile tls ps`. The relay should be `healthy`; Caddy should be `running` when a domain is enabled.

`/health` uses the `Accept` request header to serve HTML to browsers and JSON to automation, so both use the same endpoint.

The mobile pairing page ships in the same image. Open `http://<SERVER_IP>:8787/`, or `https://relay.example.com/` after configuring a domain. The deployment script checks both relay health and the embedded PWA; the root URL should display the Spcod pairing page.

## Add a domain and automatic TLS later

1. Point the domain's A/AAAA records at the server and allow TCP ports 80 and 443.
2. Run one command:

```bash
./deploy.sh --domain relay.example.com
```

The script starts Caddy, which automatically obtains and renews the TLS certificate. It also restricts the relay port to loopback, proxies WebSocket traffic through Caddy, and sets `TRUST_PROXY=true`. Certificates persist in Docker volumes. With any other upstream reverse proxy, forward the real `X-Forwarded-For` and enable `TRUST_PROXY`; otherwise `MAX_CONNS_PER_IP` (64 by default) counts every client under the proxy address.

Then change the relay URL in harness to `wss://relay.example.com`; the access key remains unchanged. See the [deployment guide](docs/DEPLOYMENT.en.md) for details.

### Ports 80/443 are already in use

The defaults remain 80/443 because they are simplest for direct public Caddy certificate issuance. To override the host ports:

```bash
./deploy.sh --domain relay.example.com --http-port 8080 --https-port 8443
```

The values persist in `deploy/relay.env`, so later `./deploy.sh` runs reuse them. With a non-standard HTTPS port, the harness URL and health page become `wss://relay.example.com:8443` and `https://relay.example.com:8443/health`.

These options only change Docker host-port mappings; Caddy still uses 80/443 inside the container. **Public certificate issuance still requires a working ACME validation path.** If Nginx or another service occupies 80/443, configure the existing reverse proxy and certificate forwarding, or free the standard ports—changing ports alone does not guarantee certificate issuance.

## Dependency versions

| Use case | Dependencies |
|---|---|
| One-command deployment | Bash, Git, Docker Engine 24.0+, Docker Buildx, Docker Compose 2.20+ (`docker compose`) |

| Local development | Node.js 22.19+, pnpm 9.15.9 |
| Relay runtime | `ws`, `tweetnacl` (used for v3 X25519 admission verification) |

The Docker image uses Node.js 22 Alpine and pins pnpm 9.15.9 during the build. The deployment script checks that Docker and Compose are available.

## Build cache and mirror acceleration

The first build downloads the Node base image, the pinned Spcod source archive, and mobile dependencies. Later builds reuse separate base-image, source, npm-download, and pnpm-store layers/caches; upgrading the PWA does not download packages that are already present. The pinned pnpm version is installed into an image layer through npm, so later stages do not rely on Corepack downloading it again.

Before building, `deploy.sh` checks `NODE_IMAGE`. If the image already exists locally it is reused without another pull; only a missing image triggers an explicit `docker pull`.

If Docker Hub or npm is slow from the server, override these values in `deploy/relay.env`:

```dotenv
NODE_IMAGE=<your-cloud-mirror>/library/node:22-alpine
NPM_REGISTRY=https://registry.npmmirror.com
```

Then run `./deploy.sh` again. `NODE_IMAGE` can also reference a Node 22 Alpine image already built or imported on the server. Obtain the Docker Hub accelerator URL from your own cloud provider console; configuring Docker daemon `registry-mirrors` also accelerates base-image downloads.

Note that `NODE_IMAGE=node:22-alpine` is still a Docker Hub tag; whether Docker routes it through a daemon registry mirror is up to Docker. If the mirror is unreliable, set `NODE_IMAGE` to a complete, directly accessible image repository path, such as `.../library/node:22-alpine` in your cloud provider's registry.

Build caches require Buildx. If the log says `buildx isn't installed`, install it on Ubuntu with:

```bash
sudo apt install -y docker-buildx-plugin
```

After the first successful build, do not run `docker system prune`, `docker builder prune`, or a `--no-cache` rebuild merely to “clean up”; those commands remove the BuildKit npm/pnpm caches. Normal `git pull && ./deploy.sh` runs reuse them.

## How it works

1. **Routes ciphertext by channel**: the channel ID is the SHA-256 hash of the desktop public key; application frames are forwarded unchanged.
2. **Queues offline messages**: ciphertext is queued by channel and direction while a peer is offline, then delivered in order. The default retention limit is 72 hours; the queue is memory-only, and clients reconnect and recover after a restart.
3. **Includes the mobile PWA**: the Docker build compiles the PWA from a pinned Spcod source commit and places it in `/app/public` in the final image, serving the relay and pairing page through the same entry point.
4. **Enforces v3 admission**: hosts obtain tickets with an HMAC-SHA256 proof keyed by the NaCl precomputed shared secret derived with X25519; devices use desktop-issued grants. Tickets are single-use and valid for 30 seconds. Self-hosted deployments add an access key by default, and public mode never bypasses v3 admission.

The relay has no account system, does not log message plaintext, and never persists the offline queue to disk. When the relay serves the same-origin PWA, it is also a code-distribution source that must be trusted in addition to the E2E protocol; self-hosting lets you control both the relay and the PWA build. Responses use a `script-src 'self'` CSP, and the PWA theme bootstrap script is external.

## Common operations

```bash
# Show service status
docker compose --env-file deploy/relay.env -f deploy/docker-compose.yml --profile tls ps

# Follow relay logs
docker compose --env-file deploy/relay.env -f deploy/docker-compose.yml logs -f relay

# Update and redeploy while preserving configuration and credentials
git pull
./deploy.sh

# Stop all services
docker compose --env-file deploy/relay.env -f deploy/docker-compose.yml --profile tls down
```

See the [self-hosting guide](docs/SELF_HOSTING.md) for environment variables, PWA origins, and reverse-proxy configuration.

To upgrade the embedded PWA, maintainers update the Spcod commit in `ARG SPCOD_PWA_REF` in the `Dockerfile` and push this repository. Official and self-hosted relays then receive the same version through `git pull && ./deploy.sh`; there is no separate upload workflow.
